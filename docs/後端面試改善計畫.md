## 3. 建議執行順序（資源有限時）

1. **K**：文件對齊（低成本、立刻減少面試認知落差）。
2. **B**：Refresh token（認證主線，技術深度最好講）。
3. **F**：CI + 補強關鍵測試（bookings 衝突、權限、取消規則、webhook 簽章等）。
4. **C、D、E**：安全與邊界（與 [P0 備忘 §6「下一步」](./P0-API收斂與安全補強備忘.md) 一致）。
5. **G → H → I → J**：依時間取捨。

## 4. 分階段驗收（精簡勾選）

### 階段一：可信度與敘事（P1）

- [ ] `SPECIFICATION`／`SPEC_INTERVIEW`／`專案介紹.md` 與現行 API、部署一致（項目 K）。

### 階段二：正式環境體質（P1）

- [ ] 非本機環境無法匿名瀏覽完整 OpenAPI（或同等保護）（項目 C）。
- [ ] CORS 僅允許已知前端來源（項目 D）。
- [ ] 敏感路由具 rate limit（項目 E）。

### 階段三：進階（P2）

- [ ] Legacy orders 路徑有明確淘汰計畫或已移除（項目 G）。
- [ ] 錯誤 JSON 含穩定欄位與 request 追蹤（項目 H）。
- [ ] `/health` 行為符合 Cloud Run／監控期望（項目 I）。

## 5. 風險與依賴

- **Refresh（B）** 需 **DB migration**（新表或欄位）與前端 401→refresh→重試；詳見 [DEVELOPMENT_PLAN_AUTH_AND_DATABASE.md](./DEVELOPMENT_PLAN_AUTH_AND_DATABASE.md)。
- **Cookie / CORS（D）** 與 **OAuth callback** 網域必須一致；Android／LINE 內建瀏覽器見同文件 §2。
- **Rate limit（E）** 若放在 gateway（例如 Cloud Run 前緣或 Vercel），需與本機 Docker 行為對照，避免面試 demo 環境落差過大。
