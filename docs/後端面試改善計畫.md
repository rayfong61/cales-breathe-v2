### CD 計畫（補充）

**現況：** 前端 **`cales-breathe-v2-vite`** 已由 **Vercel** 在 push／merge 後自動建置並部署。**後端** **`cales-breathe-v2-api`** 目標宿主為 **Cloud Run**，但目前**未**接上與 Git 同步的自動發佈（CD 缺口在後端）。

**建議方向（擇一即可，不必兩種都做）：**

1. **Cloud Build**：在 GCP 建立 **Trigger**，綁定 GitHub 的部署分支（例如 `main`），必要時設 **included files**（僅 `cales-breathe-v2-api/**` 變更才跑）。流水線：`docker build` → push 至 **Artifact Registry** → **`gcloud run deploy`**（或由 Cloud Build 的 Cloud Run deploy 步驟）。身分與權限以 **服務帳號** 為主；GitHub 與 GCP 連線較新建議 **Workload Identity Federation**，避免長效 JSON key。  
2. **GitHub Actions**：在同一 repo 新增 workflow：`on: push`/`workflow_dispatch`，於 **CI 通過後**或由 **main** 專用 job 建映像、push 至 Artifact Registry、再部署 Cloud Run。**GCP 認證**建議 **OIDC／Workload Identity Federation**，避免長效 JSON key。

**建議先釐清的設計點：**

| 項目 | 說明 |
| --- | --- |
| 部署分支 | 通常 `main` 對應 production；若有 staging，可多加一條 trigger／另一個 Cloud Run service。 |
| 與 CI 的順序 | 同一 PR：先於 GitHub Actions 跑 **pytest**，merge 後再觸發「只部署」流水線；或由 Cloud Build 內先做測試再 deploy（複雜度較高）。最小可行：**merge → 自動 build＋deploy**，測試仍仰賴 **branch protection + CI 必填**。 |
| 機密與設定 | **`runtime` env**（資料庫、JWT、OAuth 等）以 Cloud Run／Secret Manager 設定，勿 bake 進映像。 |
| DB migration | 若有 **Alembic**：需在部署流程中明示—**手動／獨立 job／啟動前 hook**—避免與滾動發佈（rollout）衝突（面試口述要能說清一種做法）。 |
| 可重現性 | Dockerfile、映像 tag（建議含 **git SHA**）、與 **`cloud run` 筆記** 對齊，方便自己三個月後還原步驟。 |

口述時可簡化成一句：**前端 Vercel 已是 CD；後端規劃 Cloud Build 或 GitHub Actions 將映像推至 Artifact Registry 再部署 Cloud Run，並把機密留在平台、映像可追溯。**

## 5. 風險與依賴

- **Refresh（B）** 需 **DB migration**（新表或欄位）與前端 401→refresh→重試；詳見 [DEVELOPMENT_PLAN_AUTH_AND_DATABASE.md](./DEVELOPMENT_PLAN_AUTH_AND_DATABASE.md)。
- **Cookie / CORS（D）** 與 **OAuth callback** 網域必須一致；Android／LINE 內建瀏覽器見同文件 §2。
- **Rate limit（E）** 若放在 gateway（例如 Cloud Run 前緣或 Vercel），需與本機 Docker 行為對照，避免面試 demo 環境落差過大。
- **後端 CD（L）** 需 **GCP 專案權限**、**Artifact Registry**、**Cloud Run 服務** 與 **Workload Identity Federation 或服務帳號**；首次接線通常比 Vercel 多幾步，建議與 [cloud run 筆記](./cloud%20run筆記.md) 同步更新實際指令與參數。
