# N+1 問題筆記（SQLAlchemy / FastAPI）

## 什麼是 N+1 問題？

N+1 是 ORM 常見的效能問題：

1. 先查一次主資料（`1` 次查詢）
2. 再對每一筆主資料各查一次關聯資料（`N` 次查詢）
3. 總查詢數變成 `1 + N`

當資料量變大時，查詢次數暴增，API 會變慢。

---

## 範例情境

假設你先查 100 筆 `Booking`，再在 Python 迴圈中讀每筆的 `booking.services`：

- 第 1 次：查全部 `Booking`
- 接著 100 次：每筆 `Booking` 各查一次 `services`

總共 101 次 SQL。

---

## 在本專案的對應

本專案在查 `Booking` 清單時有使用 eager loading，已在避免 N+1：

- `app/main.py` 的 `/bookings`、`/bookings/{booking_id}`、`/bookings/{booking_id}/cancel`
- 使用：`options(joinedload(Booking.services))`

因此 `_booking_to_read()` 內讀 `booking.services` 時，不會為每筆再額外發 SQL。

---

## 如何避免 N+1

### 1) 使用 eager loading

- `joinedload(...)`：用 JOIN 一次帶出關聯
- `selectinload(...)`：主查詢 + 一次 IN 查詢帶出關聯（常用於一對多）

### 2) 只拿需要欄位

- 減少 payload 與序列化成本

### 3) 在 list API 特別注意

- list 最容易放大 N+1（資料筆數最多）

---

## joinedload vs selectinload（簡述）

- `joinedload`
  - 優點：單次查詢可拿到關聯
  - 缺點：多對多/一對多時，JOIN 可能讓結果列數膨脹

- `selectinload`
  - 優點：避免 JOIN 膨脹，常在集合關聯表現穩定
  - 缺點：通常是 2 次查詢（不是 1 次）

---

## 快速檢查是否有 N+1

1. 開 SQL log（看是否出現大量重複查詢）
2. 觀察 list API 在資料量增加時的延遲
3. 找這種寫法：
   - 先 `.all()` 拿一批物件
   - 迴圈內存取 lazy relationship（如 `obj.children`）

---

## 本專案後續可注意點

目前已處理 `Booking.services`。
若未來在清單中也常讀 `booking.user`，可考慮一起 eager load（如 `joinedload(Booking.user)` 或 `selectinload` 策略），避免新的 N+1。
